# §v13v 付随執筆（TJR-S 特別枠・headless）

あなたは bar-exam リポジトリの TX `_lex` 1ファイルについて、正誤表の各記述に **「📖 ものがたり」帯**
（物語解説の全体＋当該記述の解説の要約＋具体例）を執筆する執筆者である。作業ディレクトリはリポジトリルート。
**対象ファイル：`{FILE}`**

**git の add/commit/push は絶対にしない**（commit はランナーが行う。復旧用の `git checkout -- {FILE}` のみ可）。
対象ファイル以外を編集しない。対象 HTML を直接 Edit しない（注入は必ずツール経由）。

## 手順

1. 素材抽出：`python -X utf8 scripts/v13v-extract.py {FILE}`
   （物語解説の各段落・正誤表の各記述の印付き原文・切断点・転用・未執筆の記述キーが出る）
   - 「土台: CSS=なし」または「ENGINE=なし」と出たら、先に
     `python -X utf8 scripts/tx-lex-verdict-redesign.py {FILE}` を実行して土台を入れる。
2. **未執筆の全記述分を執筆**（この執筆が本務。1文1文丁寧に）：
   - **story（必須／4〜6文・目安 250〜400字）** ── **体系・趣旨・実務**で書く（2026-08-28 改定・ユーザー指示）。
     旧版は「その肢がどういう着眼点で作られているか（『のみ』という限定語・向きが逆・五つを並べる）」＝
     **出題構造の解説**に寄っていた。これは学習資産にならないので書かない（解答技術は切断点／転用帯の領分）。
     次の 4 層を順に置く：
     1. **体系的位置づけ**：その論点が科目の体系のどこに座るか（制度の目的、対になる制度、三類型のどれか）。
     2. **趣旨**：条文・制度がなぜそう作られているか（保護しようとしている利益、危険、価値判断）。
     3. **考え方のコツ**：専門用語を使い、直後に生活語で開く（用語サンドイッチ）。要件（あるか無いか）と
        裁量（どの程度か）の別、条文の語尾（必要的／裁量的）、対になる規定の読み合わせ など。
     4. **実務での動き方**：誰がいつ何をするか、運用上の勝負どころ、実務・立法上の批判や最新改正。
        断定できない運用は『〜こともある』『〜が通常』と幅を持たせる（作り話をしない）。
     - 強調は `<b>` を 2〜4 か所（体系・趣旨・コツの核になる語句）。他のタグは使わない。
     - **判例の新規引用は禁止**（ファイル内＝原文・切断点・転用・答案圧縮・BASIS に書かれたものだけ。年月日・表記もそのまま）。
       条文は、六法で確認できる基本条文なら周辺条文を新たに挙げてよい（番号・項を必ず確認する）。
     - **書いてはいけないもの**：出題構造・解答技術（「『のみ』を見たら列挙と照合する」「向きが逆でないか
       確かめる」「この問題は五つを並べる」「まず主体、次に手続の順で切る」）／他記述への参照（記述N・肢N）／
       「本問」／問題ローカルの見解ラベル（見解Ⅰ・A説・第1説。見解は実体の学説名で書く）。
   - **example（具体例・必須／1〜3文・目安 60〜140字）**
     - その規範が動く**場面**を1つだけ描く（登場人物は甲・乙など。日時や金額は必要な範囲で）。
     - 抽象論の言い換えにしない。「〜な場面。だから〜になる」という形で、結論まで書き切る。
     - 記述の正誤（○×）そのものではなく、**規範の当てはまり方**を見せる。
   - 書きぶりは記述カードの THE GIST と同じ「やさしい版」（専門用語は直後に生活語で開く）。
     ただし GIST の丸写しはしない（ものがたりは**体系・趣旨・実務へ橋を架ける層**）。
3. payload JSON を一時ファイル（`/tmp/story_{番号}.json` または `%TEMP%`）に書く：
   `{"stmts": [{"n": "1", "story": "…", "example": "…"}, …未執筆の全記述分]}`
   - `n` は extract に出た記述キーそのまま（ア〜オ／1〜6 など）。
   - **半角二重引用符 `"` は本文で使用禁止**（属性を壊す。鉤括弧「」を使う）。JSON のエスケープに頼らない。
4. 注入：`python -X utf8 scripts/v13v-inject.py {FILE} <payload>`。assert で落ちたら payload を直して再実行。
5. ゲート：`python -X utf8 scripts/validate-tx-core.py {FILE}`（**ERROR 0 必須**）→
   `python -X utf8 scripts/check-tx-lex-engine.py {FILE}`（**PASS 必須**）。
   ERROR が出たら：`git checkout -- {FILE}` で戻し、payload を修正して再注入→再ゲート（最大3回）。
6. 自己照合を1回：①体系・趣旨・コツ・実務の 4 層が入っているか ②出題構造・解答技術の話を書いていないか
   ③条文番号・項が正確か（判例はファイル内記載と一致するか）④記述N・肢N・本問・問題ローカルの見解ラベルを
   書いていないか ⑤`"` が無いか ⑥具体例が抽象論の言い換えでなく場面になっているか。
7. 両ゲート PASS を確認したら、最終行に **`V13V_DONE {FILE}`** とだけ出力して終了する
   （PASS できなかった場合は `V13V_FAIL 理由` を出力し、対象ファイルを `git checkout -- {FILE}` で必ず元に戻す）。

## 品質見本（gold・刑訴TX073-075 で確定した新型＝体系・趣旨・実務）

- story（刑訴TX073 記述2・弁護人選任の効力）：
  `弁護人の地位は、<b>起訴という手続の切れ目でリセットされない</b>。刑事手続は捜査（被疑者）と公判（被告人）で呼び名も担当機関も変わるが、防御の必要は途切れずに続くから、32条1項は公訴提起前にした選任の効力を第一審まで橋渡しする（これに対し起訴後の選任は<b>審級代理の原則</b>で審級ごと＝2項）。ここで段差の付き方を体系で押さえたい。保釈という制度そのものは起訴後の被告人だけのもので、被疑者勾留に保釈はない（207条1項ただし書）。制度は起訴で始まるのに、その入口に立つ弁護人は捜査段階から連続している――この非対称が32条1項の意味である。実務でも、起訴の連絡を受けた弁護人がその日のうちに保釈を請求するのが定石で、選任し直す手続を挟むことはない。`
- example（同上）：
  `逮捕直後に選任された弁護人が、甲の起訴を知った翌日に第一審裁判所へ保釈を請求する場面。選任し直さなくても、そのまま請求できる。`
- story（刑訴TX074 記述3・逃亡のおそれ）：
  `同じ『逃亡のおそれ』でも、条文での働き方が違う。89条4号はおそれを疑うに足りる<b>相当な理由があるか無いか</b>という要件（あれば権利保釈の窓が閉じる二値の判断）、90条はおそれの<b>程度</b>を測る考慮要素（どのくらい大きいかを不利益の程度と比べる）。…（趣旨）…実務では、定まった住居・職・同居家族・身元引受人の有無、渡航歴などからおそれの程度を評価し、保証金額と住居制限で制御する。`
- example（同上）：
  `定職と同居家族があり身元引受人も付く甲。逃亡を疑う相当な理由はあると見られても、程度は高くないとして、高額の保証金と住居の制限を条件に職権で保釈が許されることがある。`
- **旧型（書かない例）**：`全体を貫く物差しは、保釈を誰が頼めるか・どの要件で許されるかで読み分けること。…『のみ』と限定する言い方は条文の列挙を狭めている。`
  ＝出題構造・解答技術の解説。これは切断点／転用帯が担う。
