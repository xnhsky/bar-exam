# §v16 解く前の🔰導入の付随執筆（TJR-I・headless）

あなたは bar-exam リポジトリの TX `_lex` 1ファイルについて、**問題文の下に置く「🔰 導入」**を書く執筆者である。
導入は、初見で見当がつかない学習者が解く前の 30 秒〜1 分で開いて「何の話か」をつかむための、既定で閉じた
案内（details）。作業ディレクトリはリポジトリルート。
**対象ファイル：`{FILE}`**（問題ID：`{ID}`）

## してはいけないこと（ランナーが機械で検出して不合格にする）

- **git の add/commit/push をしない**（commit はランナーが行う。復旧用の `git checkout -- {FILE}` のみ可）。
- **対象ファイル以外の追跡ファイルを 1 つも変えない**。ツール（scripts/）・プロンプト・docs・他の教材を直さない。
  ツールの不具合やこのプロンプトの矛盾に気づいたら、直さずに `logs/v16i-findings.md` へ書いて `V16I_FAIL` で終える。
  書いてよいのは `logs/` の下だけ。
- **対象 HTML を Edit で直接いじらない**（導入は必ず `tx-intro.py apply` で組む）。物語解説・記述カード・正誤表・
  BASIS・体系マップは 1 字も変えない（ランナーが `scope` で git と照合する）。**物語解説（.fa-narrative）から段落を
  移したり消したりしない**（Lexia が復習カードに使う一連の読み物＝前提が抜けると復習カード側が読めなくなる）。

## 型（ユーザー承認済み・gold＝刑訴TX142_lex・正典＝`docs/tx-v12.2.1-inline-lock.md` §v16）

導入は 3 面＋固定文。HTML は手で書かず、**JSON 仕様を書いてツールで組む**：

```
{"what":  "何の話？＝この問題が手続・制度のどこを扱うか（土俵）と、何がこじれているか。1〜3 文。<b> で核の語を 1〜2 個",
 "tools": [{"term": "用語", "ref": "条文（例 312条1項。無ければ空文字）", "def": "その用語・制度の定義 1 文"}, …],
 "order": "読む順番＝各記述がどの軸で分かれているか＋判定の手順（①→②→③）。どちらに倒れるかは書かない",
 "hints": {"ア": "…"}}   ← 任意。check が「解法ナビのヒントが結論を言っている」と出したときだけ
```

- **線引き（最重要）**：「記述を**読める**ようにする知識は書く／記述の**答えそのもの**になる命題は書かない」。
  - 書く＝制度の位置づけ、記述に出てくる用語の定義（何をする手続か・何と何の区別か）、判断の物差し（どの軸で分かれるか）。
  - 書かない＝**試されている要件・数字・期間・範囲・主体・向き**（「〜は不要」「〜日以内」「〜に限られる」「〜にも及ぶ」）、
    記述ごとの結論・正誤・組合せ番号、答案圧縮（素材の「答案圧縮」）と同じ文、解答技術（言い切りの肢は×・数字が
    違えば×・引っかけの中心はここ 等）。
  - 例：少年法の問題で記述が「検察官は全件を家裁に送致しなければならない」なら、「全件送致主義＝嫌疑があれば
    軽重を問わず家裁へ送る原則」と定義すると答えになる → 書かない。代わりに「少年事件は捜査→家庭裁判所の
    審判→（重い事件は）刑事裁判、と段階を進む。各記述はどの段階の話か」のように**段階・軸**を渡す。
  - 推論型（見解×事例、場面の当てはめ）は、手順の道具（判決の種類の違い・制度の定義）を渡してよい
    （gold の「管轄違い＝中身に入らない判決／無罪＝中身を調べた判決」）。それでも各記述の帰結は書かない。
  - **知識そのものを問う肢（数字・期間・条文の文言）は、導入で解けるようにしない。** 迷ったら書かない。
- **使う道具**は 0〜4 件。記述を読むのに要る用語だけ（多くて 3 件が目安）。要らなければ空配列。
- **分量**：本文（what＋tools＋order）で 150〜500 字が目安（30 秒〜1 分で読める量。上限 700 字）。
- **文体**：やさしい版。専門用語は直後に生活語で開く（「訴因＝検察官が掲げた審判の対象」）。です・ます調にしない
  （gold と同じ常体の短文）。強調 `<b>` は 1 面に 1〜2 個まで。
- **禁止（apply が拒否する）**：○×記号（掛け算の×も不可＝「と」で書く）／正解／正しい／誤り／肢N／記述N（「各記述」は可）／
  選択肢番号（組合せ1・後記1）／解答技術語（素直に・疑いすぎ・思い込みの罠・先入観・ひっかけ・言い切り）／改行／
  b・strong・em 以外のタグ。ref に全角括弧を入れない（括弧はツールが付ける）。本文中の引用は鉤括弧「」。
- 問題ローカルの記号（見解Ⅰ・Ⅱ、事例の人物X・甲）は、導入は問題文のすぐ下に出るので使ってよい
  （一問一答カードではない）。ただし「Ⅰ＝起訴状の訴因で測る」のように中身も添える。

## 手順

1. 素材：`python -X utf8 scripts/tx-intro.py materials {FILE}`
   （設問・原文ブロック・全記述と正解（確認用）・物語解説・体系マップの題・🧭段階トラック・BASIS の見出し・
   📘キーワード・答案圧縮・解法ナビのヒントが出る。40 万字の HTML を丸読みしない）。
   物語解説の「導入」段落と前半（前提・用語・物差し）が主素材。結論を述べる段落からは拾わない。
2. gold を見る：`python -X utf8 scripts/tx-intro.py extract outputs/ux/000_TX/002_刑事訴訟法/刑訴TX142_lex.html`
   （推論型＝見解×事例）と `… extract outputs/ux/000_TX/002_刑事訴訟法/刑訴TX143_lex.html`（知識型＝段階と定義だけを渡し、
   試される要件・数字・範囲は書かない）。密度・文体をそろえる。内容は流用しない。
3. 仕様を **Python の `json.dump(spec, f, ensure_ascii=False, indent=1)` で** `logs/v16i-spec/{ID}.json` に書く
   （手で JSON を打つと `"` のエスケープ漏れで壊れる）。
4. 適用：`python -X utf8 scripts/tx-intro.py apply {FILE} --spec logs/v16i-spec/{ID}.json`
   - `NG` が出たら仕様を直して再実行（禁止語・分量・構造を満たさないと 1 字も書かない）。
5. ゲート（すべて必須。どれか NG なら仕様を直して 4 から・最大 3 回）：
   - `python -X utf8 scripts/tx-intro.py check {FILE}` → `OK`（ERROR 0。WARN の「答案圧縮と同じ文」が出たら書き直す）
   - `python -X utf8 scripts/tx-intro.py scope {FILE} --spec logs/v16i-spec/{ID}.json` → `OK`
   - `python -X utf8 scripts/validate-tx-core.py {FILE}` → **ERROR 0**（WARNING は着手前からある物だけ。着手前に一度実行して控える）
   - `check-tx-lex-engine.py` は**実行しない**（ランナーが当該ファイルだけで回す）。
   直せなければ `git checkout -- {FILE}` で戻して `V16I_FAIL`。
6. 自己照合を 1 回（下の「自己照合」）。
7. 最終行に **`V16I_DONE {FILE}`** とだけ出力して終了する
   （PASS できなかったら `V16I_FAIL 理由` を出力し、`git checkout -- {FILE}` で必ず元に戻す）。

## 正確性（最重要）

- 条文番号・項は**このファイルの BASIS・📘キーワード・答案圧縮に出てくるもの**を使い、現行法で書く
  （刑訴法は令和7年法律第39号の一部施行＝2026-05-21 で 218 条の項がずれた。刑法は 2025-06-01 から拘禁刑）。
  ファイルに無い条文を足すときは e-Gov で確かめる：
  `curl -sS --fail --create-dirs -o logs/v16i-spec/law.xml https://laws.e-gov.go.jp/api/1/lawdata/<法令ID>`
  （刑事訴訟法 323AC0000000131／刑法 140AC0000000045／民法 129AC0000000089／民事訴訟法 408AC0000000109／
  商法 132AC0000000048／会社法 417AC0000000086）。確かめられない条文は書かない（ref を空にする）。
- **判例は導入に書かない**（判例の結論は答えになりやすい。判例の名前を道具に挙げる必要があるときも、
  このファイルの BASIS にあるものだけ・結論は書かない）。
- ファイルの他の箇所に誤りを見つけても**直さない**。`logs/v16i-findings.md` に「- {ID} 〔箇所〕内容（根拠）」で残す。

## 自己照合（1 回・執筆者本人）

1. 導入を読んだだけで、どれか 1 つの記述の○×が決まってしまわないか（答えになる要件・数字・範囲・向きを書いていないか）。
2. 「何の話？」で土俵（手続・制度のどこか）がつかめるか。「読む順番」は軸と手順だけで、結論を含まないか。
3. 定義と条文番号はファイル内の BASIS・答案圧縮と矛盾しないか（現行法か）。
4. 禁止語・分量（150〜500 字目安）・解答技術語に当たらないか。
5. `check`／`scope`／`validate` を通したか。
