# §v14 THE GIST ストーリー型への付随書き換え（TJR-G・headless）

あなたは bar-exam リポジトリの TX `_lex` 1ファイルについて、全記述カードの **💡THE GIST を旧型（1 段落）から
ストーリー型へ書き直す**執筆者である。作業ディレクトリはリポジトリルート。
**対象ファイル：`{FILE}`**（問題ID：`{ID}`）

## してはいけないこと（ランナーが機械で検出して不合格にする）

- **git の add/commit/push をしない**（commit はランナーが行う。復旧用の `git checkout -- {FILE}` のみ可）。
- **対象ファイル以外の追跡ファイルを 1 つも変えない**。ツール（scripts/）・プロンプト・docs・他の教材を直さない。
  ツールの不具合やこのプロンプトの矛盾に気づいたら、直さずに `logs/v14g-findings.md` へ書いて `V14G_FAIL` で終える
  （ランナーは対象外ファイルの変更を元に戻して不合格にする）。書いてよいのは `logs/` の下だけ。
- **対象 HTML を Edit で直接いじらない**（GIST は必ず `tx-gist-story.py apply` で組む）。
  THE GIST 以外（BASIS・段階解説・答案圧縮・体系マップ・記憶のフック・正誤表など）は 1 字も変えない
  （ランナーが `scope` で git と照合する。GIST 行が仕様から組んだ HTML と 1 字でも違っても不合格）。

## 型（ユーザー承認済み・正典＝`docs/tx-v12.2.1-inline-lock.md` §v14）

```
結論（○×マーク＋正しい結論一文）
🧭 現在地（問題全体の段階トラック 2〜4 段のうち今の段）＋この記述の問い
🎬 場面 → ❓ 問題 → ⚖ 判例・条文 → 🔍 理由
📘 キーワード（1〜3 語の定義）
判定（1 行＝記述のどの語が判例・条文と合う／ずれるか。×は正しい帰結まで）
```

HTML は手で書かない。**JSON 仕様を書いてツールで組む**：

```
{"track": ["段1", "段2", "段3"],
 "cards": {"1": {"mark": "×", "head": "…", "now": 0, "question": "…",
                 "scene": "…", "issue": "…", "answer": "…", "why": "…",
                 "terms": [["語", "定義"], ["語", "定義"]], "image": "…", "judge": "…"}, …}}
```

## 手順

1. 素材：`python -X utf8 scripts/tx-gist-story.py materials {FILE}`
   （設問・体系マップの文字・物語解説・各記述の本文／正解／答案圧縮／旧 GIST とリンク／段階解説／記憶のフック／
   POINT／BASIS／間違いやすいポイントが出る。40 万字の HTML を丸読みしない。足りない所だけ Grep で見る）。
2. gold 見本の仕様を見る：`python -X utf8 scripts/tx-gist-story.py extract outputs/ux/000_TX/002_刑事訴訟法/刑訴TX100_lex.html`
   （密度・文体・長さをそろえる。内容は流用しない）。
3. 全カードの仕様を **Python の `json.dump(spec, f, ensure_ascii=False, indent=1)` で** `logs/v14g-spec/{ID}.json` に書き出す
   （手で JSON を打つと、リンク属性の `"` のエスケープ漏れで壊れる）。
4. 適用：`python -X utf8 scripts/tx-gist-story.py apply {FILE} --spec logs/v14g-spec/{ID}.json`
   - `NG` が出たら仕様を直して再実行（全カード被覆・mark が正誤表の正解と同じ向き・旧 GIST のリンクの保持・
     本文 1 行・許可タグ strong/b/em/a のみでタグの開閉がそろう・track と用語はタグ無し、を満たさないと 1 字も書かない）。
   - **「GIST 行を行単位で特定できない」「1 行に収まっていない」の NG は仕様では直せない**。直さずに `V14G_FAIL` で終える。
5. ゲート（すべて必須。どれか NG なら仕様を直して 4 から・最大 3 回）：
   - `python -X utf8 scripts/tx-gist-story.py check {FILE}` → `OK`
   - `python -X utf8 scripts/tx-gist-story.py scope {FILE}` → `OK`
   - `python -X utf8 scripts/validate-tx-core.py {FILE}` → **ERROR 0**（WARNING は着手前からある物だけ。着手前に一度実行して控える）
   - `check-tx-lex-engine.py` は**実行しない**（ランナーが最後に当該ファイルだけで回す。コーパス全体を走査して数分かかる）。
   直せなければ `git checkout -- {FILE}` で戻して `V14G_FAIL`。
6. 自己照合を 1 回（下の「自己照合」）。
7. 最終行に **`V14G_DONE {FILE}`** とだけ出力して終了する
   （PASS できなかったら `V14G_FAIL 理由` を出力し、`git checkout -- {FILE}` で必ず元に戻す）。

## 各フィールドの書き方

- **track**：問題全体の段階（2〜4 段）。体系マップの枝の区分と並び順・物語解説の流れに合わせる。全カード共通の短い名詞句
  （例：令状の種類／許される要件／実施の仕方）。**now**＝そのカードが track のどの段か（0 始まり）。
- **mark**：○ か ×。materials に出る「正解」と一致させる（○×は記述＝命題の真偽。事例の成立/不成立の記号ではない）。
- **head**（常体・35 字前後まで・**述語で終える**＝「〜である。」「〜できる。」。体言止めにしない）：その記述についての
  **正しい結論**を一文で。×記述なら誤りを直した正しい命題。核の語 1 つだけ `<strong>`。
- **question**（常体・疑問）：この記述が問うていること。答えを含めない。
- **scene**（です・ます）：初学者が像を結べる具体的な場面 1〜3 文。登場人物は「被疑者」「弁護人」「検察官」「裁判官」
  「売主」「買主」など**役割名**で書く（甲・乙・A・X などの記号は使わない）。実在の事件・判例の事実を捏造しない。
  断定できない事実は仮定形で書く。
- **issue**（です・ます）：その場面で何が問題になるか。核の専門用語を 1 つ `<strong>` で使う。
- **answer**（です・ます）：判例・条文の答え。判例名・年月日はファイル内の BASIS・段階解説・答案圧縮と一致させる。
  **旧 GIST にあるリンク `<a …>…</a>` は、id があってもなくても、id・href を変えずに `<a …>` ごと GIST のどこかに残す**
  （id は BASIS の「戻る」の戻り先、href はカードから BASIS へのジャンプ。リンクの文字は現行法に合わせて直してよい）。
  条文だけで答えが出るカードは条文で答える（ラベルは「判例・条文」）。
- **why**（です・ます）：なぜそうなるか（制度趣旨・理由）を初学者向けに 2〜3 文。判例・条文が言っていない理由を
  判例の言葉のように書かない（「〜と説明されます」など、説明であることが分かる書き方にする）。
- **terms**：本文で使った専門用語 1〜3 語（基本 2 語）の定義。定義は正確に（必要なら条文番号）。
  **本文では専門用語をそのまま使い、定義はここへ出す**。本文の丸括弧の言い換えは 10 字程度の短いものまで
  （「カテーテル（尿道に入れる細い管）」程度）。文を分断する長い挿入や「——」は使わない。
- **image**：**空文字にする**（§v15・2026-09-22：🖼イメージ面は 🗝記憶のフックと逐語重複するため廃止。空なら面を出さない）。
- **judge**（です・ます）：記述のどこが判例・条文と合うか／ずれるか。×なら**正しい帰結まで書き切る**
  （何ができる・何が成立する・何が要らない等。不可罰が正しいなら不可罰と書く）。
- 本文は 1 行。1 ブロックの `<strong>` は 1〜2 個まで。用語スープ（1 文に専門用語を 3 つ 4 つ）にしない。
- **禁止**：「——」の挿入句／丸数字①〜⑩／「記述1」「肢2」「本問」「上記」／A説・B説・見解Ⅰ・学生A などの
  問題ローカルなラベル（実体の学説名で書く）／下線部・傍線部への言及／甲乙・X・Y などの人物記号／
  本文中の半角の二重引用符（鉤括弧「」を使う。リンク属性の `"` だけは残す＝json.dump が正しくエスケープする）。

## 正確性（最重要）

- **判例は、このファイルの BASIS・段階解説・答案圧縮に出てくるものだけを使う。ファイルに無い判例は、確かだと思っても
  GIST に書かない**（headless には判例検索の手段が無い。ランナーの `scope` が GIST にだけ出てくる判例の日付を検出して不合格にする）。
  用語の定義にも判例名を添えない。役に立つ判例があれば `logs/v14g-findings.md` に書くだけにする。
- **条文は番号だけでなく中身（文言・要件・期間）も現行法で書く。** BASIS が古い文言のことがある。GIST が条文の中身を述べるときは
  e-Gov の現行版で確かめ、BASIS と違えば**現行法を優先**して、違いを `logs/v14g-findings.md` に書く。
  - 取り方（Bash の curl。WebFetch は不可）：`curl -sS --fail --create-dirs -o logs/v14g-spec/law.xml https://laws.e-gov.go.jp/api/1/lawdata/<法令ID>`
  - 法令ID（2026-09-17 疎通確認）：刑事訴訟法 323AC0000000131／刑法 140AC0000000045／民法 129AC0000000089／
    民事訴訟法 408AC0000000109／通信傍受法 411AC0000000137／商法 132AC0000000048／会社法 417AC0000000086。
  - それ以外の法律は法令一覧から ID を引く：`curl -sS --fail --create-dirs -o logs/v14g-spec/lawlists.xml https://laws.e-gov.go.jp/api/1/lawlists/1`
    を Python で読み、`<LawName>` が法令名と完全一致する `<LawId>` を使う。見つからなければ条番号を書かず、法令名と中身だけにする。
  - **最高裁規則（刑事訴訟規則・民事訴訟規則など）は e-Gov API に無い**。確認できないので規則の条番号は書かない。
  - Python で `<Article Num="218"[^>]*>` → `<Paragraph Num="(\d+)"[^>]*>` を抜き出し、**UTF-8 ファイルへ書いて Read する**
    （端末表示は文字化けする）。確認できない項番号は書かずに条だけにする。
  - 既知の改正（ヒント。これ以外もあり得るので中身は必ず e-Gov で確かめる）：
    - 刑事訴訟法：令和7年法律第39号（刑事手続の IT 化）の一部が 2026-05-21 施行＝記録命令付差押え→電磁的記録提供命令、
      218条の項の繰り下がり（令状不要の特則＝4項・身体検査の条件＝9項）、179条1項・113条1項・429条1項2号・321条1項1号などの文言変更。
    - 民法：令和6年法律第33号（家族法・共同親権）が 2026-04-01 施行＝819条（離婚後の親権者は双方又は一方）、
      768条（財産分与の請求期間 2 年→5 年）ほか。令和4年法律第102号（嫡出推定・再婚禁止期間の廃止）が 2024-04-01 施行。
    - 刑法：令和4年法律第67号（拘禁刑）が 2025-06-01 施行＝懲役・禁錮→拘禁刑。
- **現行法では記述の○×が変わる（正誤表の正解が古い）と分かったときは、GIST を書かない**。`V14G_FAIL 現行法で正誤反転 …` を出力し、
  根拠を `logs/v14g-findings.md` に書く（mark は正誤表と逆にできない＝apply が拒否する。人手で問題ごと直す必要がある）。
- ファイルの他の箇所に旧法の記述や誤りを見つけても**直さない**。`logs/v14g-findings.md` に
  「- {ID} 記述N 〔箇所〕内容（根拠）」の形で追記して残す（別タスクで一括是正する）。GIST 側は正しい現行法で書く。

## 自己照合（1 回・執筆者本人）

1. mark・head・judge の向きが正解と一致し、×記述は正しい帰結まで書き切っているか。head は述語で終わっているか。
2. 判例はファイル内のものだけか。条文の番号・項・文言が現行法か（e-Gov で確かめたか）。
3. このカード単体で初学者が分かるか（場面→問題→判例・条文→理由が一本の話になっているか）。
4. image が記憶のフックと同じ像か。track と now が体系マップの枝と合っているか。
5. 旧 GIST のリンクを id・href ごと全部残したか。禁止事項（——・①・記述N・本問・ラベル・下線部・人物記号）に当たらないか。
